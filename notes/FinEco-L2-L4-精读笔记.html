0. 三讲的一句话定位与逻辑链

讲次 回答的问题 核心动词 出错时的典型症状
第 2 讲 我要什么数据、从哪里拿、拿到的是什么 定义 + 获取 数据下载下来了，但答不了研究问题
第 3 讲 多张表怎么拼成一张能用的底表 组织 程序不报错，但观测单位悄悄变了
第 4 讲 缺失/重复/极端值怎么处理、怎么证明做对了 判断 + 审计 表变"干净"了，样本和变量含义却变了

贯通逻辑：研究问题 → 数据需求说明 → 原始快照 → 粒度/主键设计 → 表操作 → 清洗判断 → 审计证据 → 可复现交付

讲义反复强调的一条主线：代码能运行 ≠ 数据正确 ≠ 结论成立。三讲分别对应"取得证据""组织证据""审查证据"三道关口。

第 2 讲 金融数据分析：流程、环境与数据获取

2.1 数据分析的七阶段流程

讲义的出发点很锋利：数据能下载下来，只说明取得了某些记录，并不说明这些记录已经适合回答手头的问题。

阶段 要完成什么 负债—盈利例子中的自问 留下什么
问题定义 把宽泛主题转成具体问题 描述关系、预测盈利，还是识别因果？ 研究问题 + 目标总体
数据获取 按对象、期间、频率取得资料 保留退市企业吗？合并报表还是母公司报表？ 原始文件、来源、下载条件
管理与清洗 统一可确认的结构，诊断异常 一行是证券年度还是公司年度？ 字典、代码、样本流
探索性分析 看分布、趋势、组间差异 差异是否由行业或异常分母驱动？ 描述统计 + 诊断解释
建模分析 使模型对应研究目标 回归系数有因果含义吗？ 模型设定 + 可执行程序
解读与评价 解释数量级、误差、适用范围 统计差异有经济意义吗？ 结论、替代解释、局限
报告与复现 让别人理解并检查 别人能从同批输入得到同样输出吗？ Notebook、环境、运行说明

三类任务，证据标准不同（同一批变量可以服务三者，但混淆即出错）：
- 描述：交代样本覆盖、变量口径、统计范围即可。
- 预测：必须区分训练期/测试期，只允许使用当时已可获得的信息。
- 因果：必须说明为什么观测差异能解释为因果作用。

讲义原话：模型形式本身不会自动决定研究问题。预测准确率高的代码改成回归形式，不会因此获得因果含义。

2.2 数据类型：按两种维度分类

按结构化程度

类型 金融例子 进入分析前的关键工作
结构化 股票日行情、年度财务表 检查键、类型、单位、时间
半结构化 API 的 JSON 响应、XBRL 财报 识别层级、提取字段、保留关联
非结构化 年报段落、公告扫描件、电话会议音频 转录/解析，再定义并验证测量规则

判断依据不是外表，而是含义和结构。半结构化数据不能"简单转成 DataFrame"，要先理解层级关系再决定哪些字段展开。多模态场景下（表格给债务存量、附注解释期限与抵押），文本提取的标签仍需验证。

结构越弱，研究者需要补充的测量规则越多。

按时间维度与生成方式

结构 变化来自 一行由什么识别
截面数据 不同对象（时间固定） 对象标识
时间序列 时间（对象固定） 时间变量
面板数据 对象 × 时间 对象标识 + 时间变量

不平衡面板不是数据遗漏：上市晚、退市都会造成公司年份不齐，不能直接判定为缺失。

生成方式还有：观测数据 / 实验数据 / 准实验（政策变化、制度边界、外部冲击）。叫"准实验"不等于可以跳过外生性与识别条件讨论；有面板不等于混杂因素自动消失。

2.3 从 DGP 到研究数据：四层形成过程

真实经营活动 → 记录与披露（会计准则、披露制度）→ 数据库整理（字段体系、报表口径、版本规则）→ 研究者筛选（样本条件）

下载到的表格不是现实本身，而是经过记录、披露、整理、筛选后的可观测结果。

三个必问问题

  1. 覆盖 Coverage：哪些企业/交易本来有机会进入记录系统？
  2. 测量 Measurement：数据库变量究竟测量了现实活动的哪一方面？
  3. 选择 Selection：研究者通过样本条件保留了哪些记录？

记号（写报告时可直接用）

令 S_it 表示企业 i 在年份 t 是否进入最终样本（进入=1），Y_it 为结果变量：
- 实际观察到的是 E(Y_it | S_it = 1)
- 目标总体是 E(Y_it)
- 若入样与盈利状况相关，两者一般不能画等号。样本量再大，也只是更精确地描述已选样本，不会自动证明样本代表总体。

强制动作：把下载条件写进研究记录

必须保存：数据库名称、导出时间、样本范围、起止期间、字段、频率、报表类型。
下载时间未知就记为 unknown——本次读取日期不能冒充最初下载日期。

Jupyter 的隐藏状态（高频坑）

Notebook 里代码可能没运行、输出可能来自更早版本；改了前面单元却只重跑后面单元，旧变量仍留在内存。
可靠检查 = 重启内核，从头到尾顺序执行一次。
若包装好了但 Notebook 提示无法导入，先查当前 Notebook 用的是不是装了该包的 Python 内核。

Git 最小工作流

git clone      # 取得已有仓库（已有副本不要重复 clone 到同名目录）
git status     # 看改了哪些文件
git diff       # 看具体改了什么
git add        # 选择本次要记录的变化
git commit     # 写入可回溯版本
git push       # 需要协作/备份时同步远程

受限数据（CSMAR）的处理原则：重点不是上传原始数据，而是留下识别信息——文件名、来源说明、下载条件、文件指纹，并让处理代码知道去授权目录找哪些输入。即使用 Git LFS，也不能绕过数据库授权。
复现 ≠ 把所有包升到最新版：先记录并恢复已验证过的包版本组合。

数据清单 manifest（与 Git 互补）

记录某次分析实际用了哪批输入文件、来自哪里、版本如何识别。Git 管代码变化，manifest 管数据输入。

2.6 获取与首次读取

pandas 读取入口与检查重点

输入 读取入口 第一次读入尤其要检查
CSV read_csv 编码、分隔符、证券代码、缺失标记
Excel read_excel 工作表、表头位置、脚注、合并单元格
Stata read_stata 标签、类别、日期、扩展缺失值转换
Parquet read_parquet schema、读取列、当前数据版本

第一次读取的四步检查（必背）

  1. shape 核对行列数，判断文件是否读全；
  2. 看前几行，识别多层表头、单位说明、脚注是否被误当数据；
  3. 检查变量类型与非缺失数量，确认标识/日期/数值没被误解释；
  4. 看描述统计，用数量级和取值范围继续查单位、异常编码、明显错误。

三类常见问题与处理顺序

  • 路径错误：FileNotFoundError → 先看当前工作目录，再核对相对路径。
  • 编码错误：中文乱码 → 先查提供方对编码的说明，再有依据地试 utf-8 / gbk。
  • 特殊缺失占位符：--、N/A 出现在数值列 → 先查清该数据源的定义，再决定是否转缺失。

两条硬规则

  • 证券代码 000001 的前导零有标识意义，通常按字符串保存。 被解释成整数 1 后补几位，必须依据该数据库编码规则，不能一律 zfill(6)。
  • 日期转换后要统计转换失败记录数并追查原因，不用任意日期填补。

"读入成功不等于解释正确"：不断改 read_csv() 参数直到不报错，不能证明数据读对了。要核对的是字段、类型、单位和缺失含义是否与原始说明一致。

在线文件与 API

先区分浏览器展示页面与程序真正要下载的数据文件（GitHub 普通页面返回 HTML，Raw 链接才返回文件本身）。

稳妥下载流程：检查 HTTP 状态 → 看响应类型与实际内容 → 确认后保存原始字节 → 记录下载时间与校验值。
返回登录页/权限提示/错误页 = 失败，不把 HTML 强行交给 pandas 解析；不通过伪装请求头绕过明确的权限控制。

API 四步：
1. 按官方文档明确端点/函数、参数、频率、单位、权限；
2. 先请求很小的时间范围核对字段、数量、日期；
3. 按文档处理分页、超时、频率限制，记录失败批次，不把失败当零条数据；
4. 保存输入快照 + 请求参数 + 版本 + 下载日期，后续分析只读该快照。

API key 配置在用户自己的环境变量或受保护配置中，不写进提示词、Notebook 输出或 Git 仓库。

持续更新 vs 课堂复现必须分开：复现分析读取一份已检查过的固定快照，否则同一段代码不同日期运行得到不同输入，无法判断结果变化来自模型还是数据更新。

AKShare 与复权（stock_zh_a_hist）

参数 symbol（证券）/period（频率）/start_date、end_date（范围）/adjust（价格调整方式）——每个参数都对应研究口径。

参数或选择 读者必须说明
股票与日期范围 选择是否依赖事后表现；边界是否包含所需支持期
日/周/月频率 用交易频率还是财务报告频率
不复权/前复权/后复权 价格调整依据与研究用途
成交量、金额、涨跌幅 原始单位，百分数与小数的区别

复权的经济含义：昨收 10 元，除息后 9 元，每股派现 1 元 → 计入分红则回报 (9+1)/10-1 = 0；只看价格则得 −10%。

三条边界：
1. 前复权/后复权本质是选择了不同的价格标度，没有哪个在所有任务中天然正确；
2. 后复权价不是当时能成交的真实价格；
3. 保存复权序列不等于前视偏误已自动消失。

必须区分"今天能查到的股票名单"和"过去某一天实际存在的可投资集合"——用当前列表回溯历史会把已退市证券从一开始排除，形成事后选择。

参数、软件版本、SHA256 和失败清单。输出覆盖与缺失汇总。
数据定义或授权不清时停止相应步骤并列出待确认事项。

第 3 讲 金融数据管理：从多张表到分析底表

3.1 多表场景与第一条纪律

典型表集合：个股日行情、市场指数、宏观月度指标、年度财务表、公司基本信息、公告、分析师预测。

第一条纪律：先确定最终一行代表什么，再决定怎样连接数据。

数据表 每行代表什么 候选键 年度研究中的用途
日行情 某证券某交易日 证券代码 + 日期 先形成年度交易特征
指数日行情 某指数某交易日 指数代码 + 日期 市场表现 / 共同时间信息
宏观月表 某指标某地区某月 指标 + 地区 + 月份 明确聚合与可得时间后连接
年度财务表 某公司某年某报表口径 公司标识 + 年度 + 报表类型 保留所需财务口径
身份历史表 某标识在某有效期间对应的对象 标识 + 有效起始时间 处理名称/代码/上市状态变化

现实复杂性：行业分类、所有权性质、证券简称、甚至证券代码都可能随时间变化——今天的公司属性不能无条件倒填到十年前。
证券代码 ≠ 公司 ID：前者是市场交易层标识，后者标识经济实体，两者未必始终一一对应。

判断一次合并是否正确，不能只看行数是否符合预期。 错误的时期属性、身份映射或报表口径完全可能在不改变行数的情况下进入底表。

3.2 粒度与主键

  • 粒度：这一行在经济上代表什么（一家公司 / 一家公司的一年 / 一只证券的一个交易日）
  • 主键：用哪些变量能唯一找到这一行

业务主键应反映自然粒度（公司年度表常用 (firm, year)）；临时流水号虽唯一，但不说明记录是什么。

候选键必要检查

设候选键 K、总行数 N、不同键值组合数 U(K)：

U(K) = N    且    Missing(K) = 0

发现键重复不能直接去重，先解释来源

合并/母公司报表并存｜季度与年度记录混合｜财报修订｜多个证券映射｜重复导出。
只有先解释重复原因，才能决定保留、展开还是删除。

错误合并为什么可能不报错（核心案例）

日行情按 firm + year 直接连年度财务表：A 公司 2020 年有 2 个交易日 → 资产 100 被复制两次；B 只有 1 个交易日 → 资产 200 出现一次；两行年度表变成三行。

最危险的数据错误往往不是程序报错，而是程序顺利运行却改变了观测单位。

正确做法：先把日表聚合到年度（A 的换手率 1 和 3 → 年均 2；B → 2），每家公司每年回到一行，再连接。

但一对多复制不总是错误：若研究问题本身就是日度的（每日收益 vs 最近一期已披露财务特征），日行情应作母表，财务信息确实需要重复到后续多个交易日。
→ 操作是否正确，取决于它是否与目标粒度一致。

3.3 四类操作（Append / Merge / Reshape / Aggregate）

mini data

  • 2024 财务表：code, year, assets（000001→100，000002→200）
  • 2025 财务表：code, year, assets（000001→110，000002→230）
  • 公司基本信息：code, industry（000001→银行，000002→房地产）
  • 日收益：code, date, ret（000001: +0.10, −0.10；000002: +0.02, +0.03）

Append：把同类记录接到下面

annual = pd.concat([fin_2024, fin_2025], ignore_index=True)

特征：列数不变，行数相加。追加前检查：列名与含义一致、单位与编码一致、时间范围是否重叠、相同主键是否跨文件重复。

文件一覆盖 2015–2020、文件二覆盖 2020–2025，直接 append 会让 2020 保存两遍。追加后仍要检查完整业务键，最好保留来源文件标签。

Merge：沿主键增加新的变量

annual = annual.merge(
    company,
    on="code",
    how="left",
    validate="many_to_one",   # 把预期写进代码
    indicator=True            # 保留每行匹配状态
)
关系 含义
one-to-one 左右键都唯一
many-to-one 左表键可多次，右表键唯一（多年财务 ← 公司行业）
one-to-many 左表一行展开成多行，只有目标粒度本就需要展开时才合理
many-to-many 双方键都多次；若无预期应暂停检查
连接方式 保留哪些键 课堂要问
left 左表全部键及匹配 右侧未匹配为什么出现
inner 两侧共同键 哪些左表观测被静默丢弃
outer 两侧键的并集 仅左/仅右/共同各多少

错误示例：年度表与日收益只按 code 合并 → 000001 的 2024、2025 两条年度记录各自匹配 2025 年两个交易日 → 2 行变 4 行，(code, year) 不再唯一，2024 年记录连上了 2025 年行情。根源是连接键没有表达两张表真正的粒度关系。

Reshape：换排列，不改信息

# 宽表 → 长表
long = wide.melt(id_vars="code", var_name="year", value_name="assets")

# 长表 → 宽表
wide = long.pivot(index="code", columns="year", values="assets")

pivot 要求行列组合唯一确定一个值。若 (code, year) 因合并/母公司报表并存而不唯一，真正缺的是 report_type 这一维，而不是用 pivot_table 自动取均值。

reshape 只改变排列，aggregate 才改变粒度。 在 reshape 时顺手取均值，已经改了原始信息。

Aggregate：把细粒度压到目标粒度

复合收益：
- 000001：(1+0.10)(1−0.10) − 1 = −0.0100
- 000002：(1+0.02)(1+0.03) − 1 = 0.0506

通用式：R_it = ∏_{d ∈ D_it} (1 + r_id) − 1（D_it 为证券 i 在期间 t 内实际纳入计算的交易日集合）

推荐顺序：识别目标粒度 → 检查各源表粒度 → 先聚合细粒度表 → 再按完整主键 merge → 检查行数与主键唯一性。

聚合规则不是"见到多行就取均值"：
- 日收益转期间收益用复合计算，不是简单平均乘天数；
- 波动率年化要说明交易日数与假设；
- 流量变量与存量变量不能用同一种加总逻辑；
- 季度报表若为年内累计值，四个季度累计数不能再次相加。

四类操作对照

操作 主要改变什么 mini data 例子 最先检查什么
append 增加同类记录行数 2024 与 2025 财务表上下拼接 列定义、单位、重叠主键
merge 沿主键增加字段或匹配记录 年度财务表接入行业 连接键与 1:1 / m:1 关系
reshape 改变同一信息的排列 year 从行变量变成列名 信息是否一一对应、键是否唯一
aggregate 改变数据粒度 日收益压到年度收益 目标粒度与统计量的经济定义

最容易造成静默错误的是 merge 和 aggregate。 每完成一步都重新检查：行数、主键、目标粒度。

3.4 存储格式也是数据契约

中间数据被多个脚本/同学复用时，数据就是契约。接收方要知道：一行代表什么、哪些变量必须存在、类型与单位、缺失编码、由哪一步生成。

格式 适合什么 额外注意
CSV 分享、小表、人工检查、跨工具交换 不保存可靠类型契约，要明确编码与读入规则
Excel 人工录入、多工作表、报告展示 表头/格式/公式与实际数值分开核对
Parquet 标准化中间表、反复分析、选择列 保存类型 ≠ 保存经济定义
SQLite 本地多表关系、SQL 查询、约束 表结构、索引、约束要明确建立
DuckDB 面向本地文件的分析查询 结果仍受原数据粒度与类型限制

Parquet 知道 roe 是浮点数，不知道 5 表示 5% 还是 500%。 经济口径仍需数据字典。

数据字典至少回答 8 项

变量叫什么｜经济含义｜来自哪个原始字段｜保存成什么类型｜单位和缺失编码｜使用哪种报表口径｜在什么时期有效｜若为构造变量用了什么公式

原始说明没给单位，就标"待确认"，不要根据数值大小猜成元或万元。

读取时只取需要的信息

Parquet 可指定列，查询引擎还能利用分区与文件统计跳过无关块；CSV 用 usecols 也能减内存，但底层仍要解析文本结构，机制不同。

存储分区 ≠ 研究样本：正式回归从 2015 年开始，但构造 2015 年平均资产需要 2014 年期初资产——2014 年仍属支持数据，不能因为不在最终回归期就从基础层永久删除。

3.5 SQLite 与 SQL

适用条件：多表关系需长期保存、查询重复出现、希望通过约束检查结构。只有几张小表时，一次性用 pandas 完全合理。

规范流程

定义表结构与约束 → 导入数据 → 核对行数、期间、键 → SQL 筛选/连接/汇总 → 必要时读回 pandas。

DataFrame.to_sql() 不知道 (firm, year) 为什么该唯一，不会自动建业务主键。要阻止重复键，必须显式建表或核验后建唯一索引。

SELECT c.industry, COUNT(*) AS n, AVG(f.assets) AS mean_assets
FROM annual AS f
JOIN company AS c ON f.firm = c.firm
WHERE f.year = 2020
GROUP BY c.industry
ORDER BY c.industry;

阅读顺序：FROM（来源）→ JOIN（接入行业）→ WHERE（筛年份）→ GROUP BY（分组）→ COUNT/AVG（汇总）。

pandas ↔ SQL

目的 pandas SQL
选列 指定列列表 SELECT
筛选 布尔条件 WHERE
排序取前几 sort_values、head ORDER BY、LIMIT
分组汇总 groupby GROUP BY + 聚合函数
连接 merge JOIN ... ON ...
检查重复组合 duplicated GROUP BY ... HAVING COUNT(*) > 1

SQL 缺失规则：COUNT(*) 数所有行；COUNT(assets) 只数非空；AVG(assets) 忽略 NULL。
→ 报告均值时必须同时给出有效样本量，否则两组均值的分母人群可能不同。

四类实际查询的设定要点

  1. 年度交易概览：从日行情汇总交易日数、平均换手率、已明确定义的收益统计，再接财务属性。某涨跌幅字段若已以百分数保存，不能再次乘 100；日频标准差不能无说明直接写成年化波动率。
  2. 异常成交日：与当年平均成交量比可做事后描述；若变成实时信号，不能用全年均值（含未来信息），要改用截至当日之前的历史基准。
  3. 日行情 × 月度指标：把月度值重复到该月所有交易日只解决频率，没解决可得性。3 月指标若 4 月中旬才发布，3 月交易日不能用于实时预测。
  4. 日行情 × 财务表：年度研究 = 日行情先聚合到公司年度再连；日度预测 = 从每个交易日出发找当时已公告且仍有效的最近一期财务信息。

统一框架：先确认目标粒度 → 再定义指标 → 最后核对信息在什么时间可得。

建库纪律

  • 输入文件与字段映射显式列出，不让程序按文件名/行数猜"这大概是哪张表"；
  • 缺必须字段时明确报告并中止，不悄悄跳过仍输出"数据库构建完成"；
  • 数据库是派生资产，与原始 CSV 分开保存，可随时从原始输入重建；
  • if_exists='replace' 只用于明确知道可完全重建的表；
  • 写入后重新读取检查类型、行数和关键查询，不是只确认 .db 文件出现了。

3.6 DuckDB 与 Parquet

工具选择不是等级，是匹配：
- pandas：几张中小规模表，需频繁清洗、变形、模型前处理
- SQLite：多张关系表长期保存、反复按键查询连接
- DuckDB：大量本地 Parquet 需直接筛选、分组、连接

换工具不会自动修复数据逻辑。 把 CSV 全转成 Parquet、或把所有表导入数据库，都不能让一个错误的主键变正确。

性能比较的前提：同一批输入、同一组列、相同筛选、相同聚合定义，先确认结果一致再比时间。

第 4 讲 数据清洗、变量构造与质量审计

4.1 什么叫"可以使用的数据"

不是"没有缺失、没有重复、分布平滑"，而是三层同时满足：

层面 含义
结构清楚 每行代表什么、哪些变量唯一识别一行、每列应是什么类型；目标是存储类型与变量角色一致，不是把所有列转成数值
语义清楚 金额单位、报表口径、缺失含义、日期角色；同一日期字段是"报告期末"还是"实际公告日"，不能从 float64/object 推断
适合当前研究 放回具体问题判断：今天的行业代码可用于当前分布，未必适合回填十年前；2025 年下载的修订后财报可用于事后描述，不一定代表 2020 年投资者当时掌握的信息

虚构贷款公告示例：「贷款 2 亿元，期限 3 年，年利率 4.2%」——金额要带单位、期限要说明按年还是按月、利率要明确存 4.2 还是 0.042。另一公告未写期限，不能因为很多贷款都是 3 年就自动填 3。

数据清洗不是把表格修得更漂亮，而是在保留证据的前提下，判断哪些差异是技术问题、哪些本来就属于经济事实。

4.2 单张表的四步检查

前提：文件已可靠读入；原始输入只读，所有转换在派生数据上完成。

  1. Step 1 核对字段结构与变量角色（标识 / 类别 / 日期 / 金额 / 比率）
  2. Step 2 核对对象与时间覆盖（缺失年份是否有制度、上市状态、覆盖原因）
  3. Step 3 检查候选主键，解释重复组合来自报表口径、版本还是实际重复
  4. Step 4 检查关键变量分布与内部关系

4.2.1 类型转换与分类变量

区分"看起来像数字"和"研究中是连续数值"：
- 证券代码：由数字组成但作用是标识，通常按字符串保存；
- 行业代码：即使为整数，也没有"行业 8 比 4 大一倍"的含义；
- 信用评级：AAA/AA+/AA 有顺序，但相邻等级经济距离未必相等。

转换按变量角色判断，不是把所有可转数字的列都转数值。关键变量保留原始列或来源说明，并统计转换失败记录数与失败值。

金额清洗的铁律：先识别单位再换算，不要"删除所有非数字字符"——同列有 2 亿元 和 8000 万元 时，删单位后只剩 2 和 8000，反而不可比。

日期变量要明确角色：2025-12-31 可能是交易日、报告期末、公告日或下载日期。解析失败转 NaT 要报告新增缺失数及原始值，不能静默。

4.2.2 缺失：先解释为什么没有值

至少区分五种：未发生 / 不适用 / 未披露 / 数据库未收录 / 读取失败——表格里都表现为同一个缺失符号，经济含义完全不同。

企业 研发 资产 已知含义
A 0 100 明确记录为零
B 缺失 100 原因不清楚
C 2 100 明确记录为正
  • 只用 A、C：平均研发率 = (0 + 0.02)/2 = 1%
  • 把 B 填 0：三家平均 = (0 + 0 + 0.02)/3 ≈ 0.67%

统计量变了，但没有获得关于 B 的新信息——变化来自额外假设（未知当零）和分母样本变化。

四种处理及代价：
| 处理 | 代价 |
|---|---|
| 删除缺失记录 | 缺失若集中于某类企业，会系统性改变研究对象 |
| 简单填补（均值） | 人为压缩变异，不能恢复与其他变量的原有关系 |
| 增加缺失指示变量 | 可描述谁更易缺失，但不消除样本选择偏误 |
| 模型化插补 | 需明确缺失机制、插补模型与推断方法，不是万能修复 |

还要看缺失发生在哪里：按年份、行业、上市状态统计缺失率；注意多变量联合可用样本量——单字段只缺 5%，但十个变量同时非缺失时完整样本可能明显缩小。

4.2.3 重复：区分记录重复与对象不同

发现重复键先解释四类来源：
1. 完全重复导出（同批记录被重复保存）
2. 报表或频率维度未进入主键（A/B 报表共存、季度与年度混合）
3. 版本差异（同一报告日多个修订版本，需追查各版本可得时间）
4. 身份映射差异（同一公司同年对应多个证券 → 问题从去重转向公司—证券映射）

即使两行所有数值相同，也要先确认它们代表同一经济记录，而不是两类记录碰巧取值一致。

drop_duplicates() 能执行去重规则，却不能替研究者决定什么才算重复。删除必须有明确依据并留下原始数量与处理规则。

4.2.4 异常值：阈值是检查入口，不是删除名单

三类排查方向：技术错误（单位混用、录入错误、字段错位、解析失败）｜比率结构（分母接近零）｜真实经济状态（危机、重组、特殊交易）。

要同时查看原始分子分母、前后年份、相关科目，必要时回到公司披露核对。箱线图、极端分位数、z 分数只是诊断工具。

术语区分：统计分析中标准化变量通常指减均值除标准差的尺度变换；数据工程中标准化数据有时仅指统一字段名、类型、格式。

对数变换不能只当美化操作：零值和负值不能直接取自然对数；log(x+1) 是否合理取决于单位（元还是亿元），不是通用排错方法。

4.3 缩尾、截尾与样本选择

  • 缩尾 winsorization：保留观测，把尾部数值改到指定分位点
  • 截尾 trimming：把规定范围外的观测从当前样本删除

缩尾公式：x^w_it = min{ max(x_it, q_a), q_{1−a} }，其中 a 为尾部比例（如 0.01）

纪律：
- 缩尾应生成新变量，保留原始值，并记录上下尾各有多少观测被改变；
- 阈值口径要写明：全样本 1% / 逐年 1% / 行业内部分别计算，结果不同；小样本时分位数插值方式也重要；
- 不在 0.5%、1%、2% 之间反复试到回归结果符合预期；
- 基础数据层保留原始值，只有具体研究版本才执行已确认的缩尾/截尾规则。

4.3.1 基础库与论文样本分开

  • 修复错误（merge 主键设错导致复制记录）= 实现问题，必须修正；
  • 定义研究样本（排除金融行业、删 ST、要求连续 N 年有数据）= 研究设计，不应反向写进基础数据库永久删除。

两个经典偏差：用今天仍上市的公司回溯过去 → 漏掉后来退市企业；要求连续五年财务齐全 → 同时排除最近上市和较早退出的公司。
→ 先写清目标总体，再逐步记录每道筛选，不能把最后能顺利 merge 出来的交集天然当成研究样本。

4.3.2 样本流怎么记

每步记录：输入数量 → 处理条件 → 输出数量 → 原因，并保证规则可通过代码重执行。

不只是"删了多少行"：Append 会增加记录，错误的一对多 merge 也会增加记录，outer merge 会产生仅左/仅右/共同三类。

未匹配记录不能只看总体比例：按年份和有经济含义的群体继续比较未匹配率，以各组自身样本数为分母（不是只比绝对条数）。总体匹配率 95%，仍可能某个小规模群体几乎全部匹配失败。

4.4 财务比率：让公式对应经济含义

4.4.1 Leverage

Leverage_it = Liabilities_it / Assets_it
- 分子：年末负债合计；分母：同一天总资产；同一种合并报表口径
- 无货币单位；0.6 表示负债约占资产 60%
- 分母为零 → 保留为不可计算；分子或分母缺失 → 结果继续缺失，不自动填零
- Leverage > 1 不自动说明数据错误，可能反映负权益等真实财务状态

4.4.2 ROA：净利润是流量，总资产是存量

ROA^eop_it = NetIncome_it / Assets_it
ROA^avg_it = NetIncome_it / ((Assets_it + Assets_{i,t−1}) / 2)

教学数字（净利润 10、期初资产 100、期末资产 200）：
- ROA^eop = 10 / 200 = 5%
- ROA^avg = 10 / 150 ≈ 6.67%

原始数据相同，差异完全来自分母定义。 期初期末平均只是两时点近似，不等于全年每天真实资产规模的精确平均。最终比率统一用小数，0.05 表示 5%。

4.4.3 ROE：极端值先看权益

  • 期末口径：NetIncome_it / Equity_it
  • 平均权益口径：分母换成 (Equity_it + Equity_{i,t−1}) / 2
  • 关心母公司普通股股东收益 → 用"归母净利润 / 归母权益"
  • 区分"归母权益"与"母公司单体报表权益"，两者不是同一概念

极端例子：净利润 1、权益 0.01 → ROE = 1/0.01 = 100，即 10,000%。
→ 这首先说明分母几乎为零，不是盈利能力惊人。先查权益大小与符号，再看净利润，并确认报表口径一致。近零或负权益会让比率失去通常解释，需要单独诊断，不是靠缩尾压回正常范围。

本课不宣布某个 ROE 公式唯一正确，而是保留候选定义与原始分子分母，等研究问题明确后再决定。

4.4.4 Top1：构造同时保留可审计字段

十大股东表中 rank=1 时，字段 S0301b 给出第一大股东持股百分比。
做法：保留原始百分数 top1_pct，再除以 100 生成 top1，同时保留持股数量以便用总股本交叉检查。

变量转换不应只留最终比例而丢掉可帮助审计的原始字段。

4.5 怎样知道 Agent 做对了

代码执行成功只能证明程序没中断。把验证拆成可观察层次：结构 → 样本变化 → 合并关系 → 数值分布 → 信息时间。

4.5.1 结构、样本流与合并

  1. 结构审计：年份/证券/公司覆盖；分别验证证券层面与公司层面主键
  2. 样本流：每步前后样本量、增/减原因、筛选规则
  3. 合并审计：双方匹配 / 仅主表 / 仅使用表三类分开报告，追查未匹配集中在哪些群体

读合并审计不要停在"匹配率 97%"——更该问那 3% 是谁。新上市公司可能缺上一年财务，退市公司可能缺完整年度收益，金融企业某些会计项目不适用、缺失模式不同。

4.5.2 分布与会计关系

目的不是追求漂亮正态分布，而是确认数量级与内部关系可解释。
主要变量报告：非缺失样本数、均值、标准差、最小值、p1、p25、中位数、p75、p99、最大值。
p99 与最大值差几个数量级，只说明尾部有少量极端观测 → 回到具体记录查分子分母与原始来源，不是看到最大值大就缩尾/删除。

资产负债表内部核查：Assets_it ≈ Liabilities_it + Equity_it
- 只有口径一致时才有意义：同一企业、同一年末、同一报表类型、同一金额单位
- 约等号是因为存储精度与舍入
- 技术容差取 1 个原始金额单位 与 资产绝对值的 1e−8 中较大者；只为识别需人工检查的记录，不是新会计规则

4.5.3 时间审计：哪一天才知道这条信息（金融研究最容易犯的错）

四类日期：
- fiscal_year：财务所属年度
- report_date：报表统计截止日
- predisclosure_date：首次预约披露日
- actual_announcement_date：实际对外披露日期

做事后财务描述，报告期末可能足够；做交易预测或事件分析，关键是信息何时进入市场。

前视偏误示例：2025 年年报报告期末 2025-12-31，实际 2026-04 才披露。研究 2026 年 1 月的投资决策时，不能因为数据属于 2025 财年就放进 1 月信息集——投资者当时还没看到最终年报。

更隐蔽的版本问题：今天从数据库下载的财务数值可能已包含后来更正或重述，而表中公告日期只记录最初披露时间。→ 有实际披露日，仍不足以自动证明完整的历史可得性；高要求场景还需财报版本链，高频场景甚至要区分公告发生在交易时段之前/之中/之后。

4.6 从论文和复现包学习数据规则

不能把参考文献里的处理照搬。论文正文受篇幅限制，具体筛选、时间对齐、变量构造常只出现在 README、附录或代码里。

案例：Chen & Zimmermann (2022) Open source cross-sectional asset pricing, Critical Finance Review, 11(2), 207–264
- 仓库：https://github.com/OpenSourceAP/CrossSection/
- AssetGrowth.py、CompustatAnnual.py

关键陷阱：shift(12) 在 pandas 中本质上只是向前移动 12 行。只有当上游已保证同一证券按月份连续、排序正确时，这 12 行才真正对应 12 个月。→ 不能原封不动移植到存在年份断档的 CSMAR 公司年度数据上。

阅读复现包按固定维度整理：

  • 不能从一个变量构造脚本推断整篇论文最终用了多少样本（筛选可能在更上游或更下游）
  • 区分"代码公开"与"原始数据公开"：该项目公开大量程序，但部分输入仍来自受限数据库

4.7 非结构化数据与 LLM

测量链条：Y*_it → Text_it → Model → Ŷ_it
- Y*_it：真实目标状态（如是否存在供应链风险）
- Text_it：研究者实际能取得的文本
- Model：完整测量程序（模型版本、提示词、解析规则）
- Ŷ_it：进入统计分析的标签

文本没写"供应链风险" ≠ 真实风险不存在；模型输出 1 ≠ ground truth。 模型只是在既定文本与规则下给出估计标签。

二元分类最少报告三指标：
- Accuracy：所有记录中判断正确的比例
- Precision：判为正的记录中真正为正的比例
- Recall：真正为正的记录中被找到的比例

正类占比很小时，全判负也可能得到很高 accuracy → 不能用单一总体正确率评价。还要看错误集中在哪里（某行业、较早年份、超长年报、特殊措辞）；若系统性错误与后续回归分组变量相关，就可能扭曲结论。

必须保存：文本来源、抓取时间、是否截断、模型版本、提示词、推理参数、人工复核结果。

4.8 把研究规则写成可执行协议（DATA_PROTOCOL.md）

四层结构：
1. 全局规则：原始数据只读、不猜变量定义、不静默删行
2. 项目规则：研究总体、期间、目标粒度、授权边界
3. 任务规则：某一步读什么、允许怎样处理、产出什么
4. 审计规则：完成后必须报告哪些结构、样本、数值检查结果

好处：多个 Agent 任务共享稳定约束，不必每次在提示词里重述，减少不同任务用不同临时规则的风险。

以构造 Leverage 为例，规则不能只写"负债除以资产"，还要包括：分子分母各用哪个原始字段｜报表口径｜单位如何统一｜缺失如何传播｜分母为零怎么办｜是否保留原始变量｜Leverage > 1 不能自动删除。

执行后不只给新列，还要报告分布与各种不可计算原因。协议报告片段：

HUMAN REVIEW REQUIRED
问题：研发字段存在缺失。
证据：字段说明与分年缺失表尚不能区分零投入与未披露。
当前处理：保持缺失，保留原记录，不自行填零。
需要补充：披露制度、字段定义和本研究的经济口径。
影响：研发相关分析的样本和结果尚不能冻结。

四种状态不能全部压缩为"已完成"：数据审计通过｜代码工程上运行通过｜研究口径由教师或研究者批准｜最终可以公开发布。

附录 C：自测题（含答案要点）

Q1 一张证券日表和一张公司年表，粒度与候选主键分别是什么？

日表：一只证券一个交易日，候选键 (证券代码, 日期)；年表：一家公司一个年度（可能还要加报表类型），候选键 (公司标识, 年度[, 报表类型])。

Q2 同一张财务表连到年度描述数据和日度预测数据，为什么条件不同？

年度研究：日行情先聚合到公司年度再连，财务只需当年一份。日度预测：从每个交易日出发，取当时已公告且仍有效的最近一期财务信息，并允许同一期财务重复到多个交易日。差别在于目标粒度与信息可得时点。

Q3 CSV、Parquet、SQLite 各能保存什么结构信息？哪些经济定义仍需字典？

CSV：几乎不保存类型契约；Parquet：较好保存字段 schema 与类型；SQLite：可保存表结构、索引与约束。三者都不知道 roe=0.05 的经济含义——单位、报表口径、缺失编码、有效时期、构造公式仍需数据字典。

Q4 跨年份 append 后出现重复键，怎么查？

① 检查两文件时间范围是否重叠；② 保留来源文件标签，按来源分组看重复集中在哪年；③ 检查重复是完整重复还是某几列不同（报表口径/频率维度未入主键）；④ 解释来源后再决定保留、展开还是删除；⑤ 记录处理前后行数与规则。

Q5 (000001, 2022) 出现两行，report_type 为 A 和 B，能 drop_duplicates() 吗？

不能。这是两种报表口径，不是记录重复。正确做法是把 report_type 纳入主键，或按研究口径明确选定其一并记录依据。

Q6 ROA 用期末资产还是平均资产？差异从哪来？

净利润是流量、资产是存量。期末口径 NI/Assets_t，平均口径 NI/((Assets_t + Assets_{t−1})/2)。例子：NI=10、期初 100、期末 200 → 5% vs 6.67%。差异完全来自分母定义，原始数据相同。报告时必须写明用的是哪一种。

Q7 ROE = 100（10,000%）说明什么？

首先说明分母（权益）接近零，不是盈利能力惊人。应先查权益大小和符号、再看净利润、确认报表口径一致；近零或负权益让比率失去通常解释，需单独诊断，不能靠缩尾压回正常范围。

Q8 2025 年年报，报告期末 2025-12-31，实际 2026-04 披露。研究 2026 年 1 月投资决策时能用吗？

不能放进 2026 年 1 月的信息集，投资者当时还没看到最终年报——这是前视偏误。做交易预测/事件分析必须用 actual_announcement_date；做事后财务描述才可以用报告期末。

Q9 匹配率 97%，可以直接用吗？

不能直接下结论。要按年份和有经济含义的群体（新上市、退市、金融行业等）分别算未匹配率，且以各组自身样本数为分母。总体 95% 也可能某个小群体几乎全部匹配失败。

Q10 shift(12) 一定是滞后 12 个月吗？

不一定。pandas 中它只是向前移动 12 行。只有上游已保证同一证券按月份连续、排序正确时，才真正对应 12 个月。存在年份断档的公司年度数据上不能照抄。
